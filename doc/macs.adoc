[#hash-macs]
== Message authentication

A message authentication code (MAC) is a digest that only the holders of a
secret key can compute. A server that signs its session cookies, an API that
checks a request came from a client holding its key, a webhook receiver that
checks the sender, and a chat protocol that rejects altered messages all do
the same thing: the sender computes a tag from the key and the message, the
receiver computes it again and accepts the message only if the two tags are
equal. Without the key an attacker can neither forge a tag for a new message
nor change a message and keep its tag. A MAC does not hide the message, and it
does not prove to a third party who wrote it (both sides hold the key); that
is a signature's job, webcpp::crypto's.

[#hash-hmac]
=== HMAC

HMAC (RFC 2104, 1997) turns any digest into a MAC: it hashes the key, padded
to a block, with the message, then hashes that result again under the key
padded another way. The double pass is what makes it safe over SHA-2 despite
length extension, and HMAC remains secure even over hashes whose collision
resistance is broken. HMAC-SHA-256 signs JSON Web Tokens (HS256), drives
TLS 1.3's key schedule through HKDF, and is in every browser's WebCrypto.
hash re-exports Boost.Hash2's `hmac<H>` and one alias per Hash2 digest.

*Pitfalls.*

* *Compare tags with `webcpp::crypto::equal`, never with `==`.* The digest's
`operator==` is `memcmp`, which returns at the first byte that differs; an
attacker who sends guesses and times the answers learns how many leading
bytes are right and builds a valid tag one byte at a time, in a few thousand
tries per byte instead of 2^256^ in all. `equal` reads every byte whatever the
data.
* *A key is random and as long as the digest.* A 32-byte key from
`webcpp::crypto::random_device` for HMAC-SHA-256; a password is not a key
(<<hash-password-hashing>>). A key longer than the hash's block is hashed
first, which gives it no more strength.
* *Authenticate everything the receiver acts on.* A tag over the body alone
lets an attacker change the headers, the recipient or the order of messages;
put a version, the context and a counter or timestamp inside the
authenticated bytes, with an unambiguous encoding (lengths, not separators).
* *Truncate only on purpose.* A tag cut to 16 bytes still gives 128 bits
against forgery; one cut to 4 bytes gives an attacker a one-in-four-billion
chance per try, which a busy server can reach.

[#hash-siphash]
=== SipHash

SipHash (Aumasson and Bernstein, 2012) is a keyed hash made for one job:
protecting hash tables whose keys come from someone else. A hash table puts
each key in a bucket chosen by its hash; with an unkeyed hash, FNV or
MurmurHash or xxHash, anyone can compute in advance thousands of keys that
fall in one bucket, send them as the names in a form, the fields of a JSON
document or the ids of peers, and turn every lookup into a scan of a long
list: a denial of service called hash flooding. With SipHash keyed by a secret
random key per process, the attacker cannot predict the buckets. Python's
dictionaries, Rust's `HashMap` and the Linux kernel use it for that reason.
`siphash_64` is SipHash-2-4 with a 16-byte key and a 64-bit result;
`siphash_32` is HalfSipHash-2-4, the 32-bit variant for small machines, with
an 8-byte key and a 32-bit result.

This section adapts the guidance of libsodium's documentation on short-input
hashing (`hashing/short-input_hashing.md` of
https://github.com/jedisct1/libsodium-doc[libsodium-doc], ISC licence, kept in
`NOTICE.md`), in hash's own terms.

*Pitfalls.*

* *The key is the protection.* A key that an attacker can read or guess (a
constant, a seed from the time) gives no protection at all; draw it from
`webcpp::crypto::random_device` when the process starts, and keep it secret.
* *Not a digest and not a MAC for messages.* 64 bits are too few to resist
collisions found on purpose, and 32 bits far too few: SipHash protects the
shape of a table, not the integrity of data. Use HMAC (<<hash-hmac>>) for
messages.
* *Use every bit when choosing a bucket.* A table that keeps only the low bits
of the hash, or reduces it by a power of two, throws away part of what the key
protects; a prime number of buckets, or a multiply-and-shift reduction, keeps
them.

[#hash-kmac]
=== KMAC

KMAC (NIST SP 800-185, section 4) is a MAC built on cSHAKE, the SHA-3
family's own: where HMAC wraps a hash twice around the key to protect it from
the hash's structure, KMAC needs no wrapping, since SHA-3's sponge already
keeps its state hidden. It takes a key, the message and a customisation
string that separates one application's tags from another's under the same
key, and gives a tag of any length; NIST's key derivation (SP 800-56C) uses it
too. Like TupleHash, it has a fixed-length form, which encodes the tag's
length, and an XOF form, KMACXOF, which does not. `macs::kmac_128` and
`macs::kmac_256` are tags of `mac` (<<hash-mac-family>>), on
`backends::xkcp`, their default; a program links `/third_party//xkcp`.

*Pitfalls.*

* *Compare with `webcpp::crypto::equal`.* As for every tag (<<hash-hmac>>).
* *The key sets the strength.* SP 800-185 (section 8.4.1) forbids a key
shorter than the security the application needs: 16 bytes for KMAC128, 32
for KMAC256. `mac` takes any key, the empty one included, as the standard
defines it; choose its size.
* *At least 4 bytes of tag.* SP 800-185 (section 8.4.2) forbids a tag of
fewer than 32 bits and asks for a careful analysis below 64; `mac` refuses a
tag under 4 bytes with `invalid_output_size`. Prefer 16 bytes or more.
* *The form is part of the tag.* KMAC128 and KMACXOF128 of the same inputs
differ, and a fixed-length tag of 16 bytes is not the start of one of 32:
the receiver uses the sender's form and length.

[#hash-mac-family]
=== A MAC in one call: `mac`

`mac` computes the tag of a message under a key in one call, through a tag of
`webcpp::hash::macs`, as `macs::hmac<digests::sha2_256>`, HMAC over the digest
`digests::sha2_256`, and a backend: the tag's default, or the one the call
names. Its guards are the same on every backend: an HMAC tag is 10 bytes up to
the digest's size, a shorter one being the digest cut (RFC 2104, section 5);
a key of a size the MAC does not take is `invalid_key_size`. The Hash2 aliases
of <<hash-hmac>> stay the way to feed a message in pieces.

*Pitfalls.*

* *Compare with `webcpp::crypto::equal`.* As for every tag (<<hash-hmac>>).
* *A cut tag is a weaker tag.* Ten bytes, 80 bits, is the shortest `mac`
gives; keep the whole digest unless a protocol fixes a shorter tag.
* *The tag's name is the digest's.* `macs::hmac<digests::sha2_512>` cut to 32
bytes is not HMAC over SHA-512/256 (`macs::hmac<digests::sha2_512_256>`): the
two give different tags.
* *BearSSL's HMAC is reached by name.* `backends::bearssl` has HMAC over MD5,
SHA-1 and the four SHA-2s it has, any key and any tag `mac` accepts, but is
never a default: name it, as
`mac<macs::hmac<digests::sha2_256>, backends::bearssl>`, and link
`/third_party//bearssl`.
* *Keyed BLAKE2s on `backends::hash2` is 32 bytes.* `macs::blake2s_mac` takes
a tag of 1 to 32 bytes, but BLAKE2s's output size is a parameter of the hash,
not a cut: `backends::hash2` (Boost.Hash2's keyed `blake2s_256`) answers
`unsupported_by_backend` to a shorter tag. `macs::siphash_2_4` on it is
SipHash-2-4 whole: a 16-byte key and an 8-byte tag.

[#hash-siphash-sodium]
=== SipHash on libsodium: `macs::siphash_2_4x`

`mac` computes SipHash through two tags: `macs::siphash_2_4`, SipHash-2-4 with
its 8-byte result, on `backends::hash2` (Boost.Hash2's `siphash_64`, the
default) or on `backends::sodium` (libsodium's `crypto_shorthash_siphash24`),
which give the same bytes; and `macs::siphash_2_4x`, the same rounds with a
16-byte result (the SipHash reference implementation's 128-bit output,
libsodium's `crypto_shorthash_siphashx24`), on `backends::sodium` alone, its
default. Both take a 16-byte key. The 16-byte result makes collisions between
honest keys rare enough for a table or a filter of billions of entries, or for
a short identifier keyed against flooding, where 64 bits would collide; it is
still a hash for tables, not a MAC for messages (<<hash-siphash>>).

*Pitfalls.*

* *The pitfalls of <<hash-siphash>> hold:* a random key per process, and not
a MAC for messages: use HMAC there.
* *SipHash-2-4x is not two SipHash-2-4 tags.* Its 16 bytes are another
function's output, and its first 8 bytes are not SipHash-2-4's tag: a program
that must agree with another names the same tag.
* *The tag is written little-endian.* `mac` writes SipHash-2-4's 64-bit result
as 8 bytes, least significant first, as the reference implementation and
libsodium do; the `result()` of `siphash_64` is the number itself.

[#hash-hmac-sodium]
=== HMAC on libsodium

`mac` computes HMAC over SHA-256 and SHA-512 on `backends::sodium` too, with
libsodium's `crypto_auth_hmacsha256` and `crypto_auth_hmacsha512` functions,
named in the call: the same tags as the default, `backends::hash2`, for a
program that already links libsodium or that wants its implementation.
libsodium names a third HMAC, `crypto_auth_hmacsha512256`, "HMAC-SHA-512-256":
it is HMAC-SHA-512 cut to 32 bytes, which `mac` over `digests::sha2_512` gives
with a 32-byte output, and not HMAC over SHA-512/256
(`macs::hmac<digests::sha2_512_256>`), a different function that libsodium
does not have.

*Pitfalls.*

* *The pitfalls of <<hash-hmac>> hold:* compare tags with
`webcpp::crypto::equal`, and use a random key, not a password.
* *"HMAC-SHA-512-256" has two meanings.* A program that must agree with
libsodium's `crypto_auth_hmacsha512256` names `macs::hmac<digests::sha2_512>`
and a 32-byte output; one that follows a standard naming HMAC over
SHA-512/256 names `macs::hmac<digests::sha2_512_256>`. The two give different
tags.
* *A key of any size.* libsodium's one-call functions take a 32-byte key
alone; `mac` on `backends::sodium` takes a key of any size, hashed first when
it is longer than the block, as RFC 2104 says and as every other backend does.
