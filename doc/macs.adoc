[#hash-macs]
== Message authentication

A message authentication code (MAC) is a digest that only the holders of a
secret key can compute. A server that signs its session cookies, an API that
checks a request came from a client holding its key, a webhook receiver that
checks the sender, and a chat protocol that rejects altered messages all do
the same thing: the sender computes a tag from the key and the message, the
receiver computes it again and accepts the message only if the two tags are
equal. Without the key an attacker can neither forge a tag for a new message
nor change a message and keep its tag. A MAC does not hide the message, and it
does not prove to a third party who wrote it (both sides hold the key); that
is a signature's job, webcpp::crypto's.

[#hash-hmac]
=== HMAC

HMAC (RFC 2104, 1997) turns any digest into a MAC: it hashes the key, padded
to a block, with the message, then hashes that result again under the key
padded another way. The double pass is what makes it safe over SHA-2 despite
length extension, and HMAC remains secure even over hashes whose collision
resistance is broken. HMAC-SHA-256 signs JSON Web Tokens (HS256), drives
TLS 1.3's key schedule through HKDF, and is in every browser's WebCrypto.
hash re-exports Boost.Hash2's `hmac<H>` and one alias per Hash2 digest.

*Pitfalls.*

* *Compare tags with `webcpp::crypto::equal`, never with `==`.* The digest's
`operator==` is `memcmp`, which returns at the first byte that differs; an
attacker who sends guesses and times the answers learns how many leading
bytes are right and builds a valid tag one byte at a time, in a few thousand
tries per byte instead of 2^256^ in all. `equal` reads every byte whatever the
data.
* *A key is random and as long as the digest.* A 32-byte key from
`webcpp::crypto::random_device` for HMAC-SHA-256; a password is not a key
(<<hash-password-hashing>>). A key longer than the hash's block is hashed
first, which gives it no more strength.
* *Authenticate everything the receiver acts on.* A tag over the body alone
lets an attacker change the headers, the recipient or the order of messages;
put a version, the context and a counter or timestamp inside the
authenticated bytes, with an unambiguous encoding (lengths, not separators).
* *Truncate only on purpose.* A tag cut to 16 bytes still gives 128 bits
against forgery; one cut to 4 bytes gives an attacker a one-in-four-billion
chance per try, which a busy server can reach.

[#hash-siphash]
=== SipHash

SipHash (Aumasson and Bernstein, 2012) is a keyed hash made for one job:
protecting hash tables whose keys come from someone else. A hash table puts
each key in a bucket chosen by its hash; with an unkeyed hash, FNV or
MurmurHash or xxHash, anyone can compute in advance thousands of keys that
fall in one bucket, send them as the names in a form, the fields of a JSON
document or the ids of peers, and turn every lookup into a scan of a long
list: a denial of service called hash flooding. With SipHash keyed by a secret
random key per process, the attacker cannot predict the buckets. Python's
dictionaries, Rust's `HashMap` and the Linux kernel use it for that reason.
`siphash_64` is SipHash-2-4 with a 16-byte key and a 64-bit result;
`siphash_32` is HalfSipHash-2-4, the 32-bit variant for small machines, with
an 8-byte key and a 32-bit result.

This section adapts the guidance of libsodium's documentation on short-input
hashing (`hashing/short-input_hashing.md` of
https://github.com/jedisct1/libsodium-doc[libsodium-doc], ISC licence, kept in
`NOTICE.md`), in hash's own terms.

*Pitfalls.*

* *The key is the protection.* A key that an attacker can read or guess (a
constant, a seed from the time) gives no protection at all; draw it from
`webcpp::crypto::random_device` when the process starts, and keep it secret.
* *Not a digest and not a MAC for messages.* 64 bits are too few to resist
collisions found on purpose, and 32 bits far too few: SipHash protects the
shape of a table, not the integrity of data. Use HMAC (<<hash-hmac>>) for
messages.
* *Use every bit when choosing a bucket.* A table that keeps only the low bits
of the hash, or reduces it by a power of two, throws away part of what the key
protects; a prime number of buckets, or a multiply-and-shift reduction, keeps
them.
