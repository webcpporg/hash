[#hash-password-hashing]
== Password hashing

Every service that has a login will one day lose its database, through a
breach, a backup left open or an insider. What the attacker then holds is what
the service stored for each password, and what it costs to recover the
passwords from it is the service's last defence: people reuse passwords, so a
recovered password opens their mail and their bank. A password hash is a
function made to be slow and to need a lot of memory, so that every guess
costs the attacker time and memory too, on a graphics card as on a server, and
a random salt per password, so that each guess tests one user and no table can
be computed in advance. The same functions turn a password into an encryption
key for a password manager or an encrypted backup.

This chapter adapts the guidance of libsodium's documentation on password
hashing (`password_hashing/default_phf.md` and `password_hashing/scrypt.md`
of https://github.com/jedisct1/libsodium-doc[libsodium-doc], ISC licence, kept
in `NOTICE.md`), in hash's own terms; every function here runs on libsodium by
default, and on OpenSSL where the call names `backends::openssl`.

[#hash-argon2id]
=== Argon2id

Argon2 won the Password Hashing Competition in 2015 and is RFC 9106 (2021).
It fills a large matrix of 1 KiB blocks, each computed from earlier ones with
BLAKE2b, over a number of passes; an attacker who keeps less memory must
compute blocks again, at a cost that grows fast. Argon2id is its hybrid
variant, which resists both the side channels of data-dependent memory access
(in its first half pass) and trade-offs between time and memory: RFC 9106 and
OWASP name it the first choice. `argon2id` runs libsodium's by default, with
parallelism 1 (one lane), no secret and no associated data; a program links
`/third_party//sodium`. `argon2id<backends::openssl>` runs OpenSSL's, with the
same costs and the same tag, on native, wasip2 and wasip3 (a program links
`/webcpp/hash//openssl`).

*Choosing the costs.* `argon2id_parameters` has two: `memory`, in bytes, a
multiple of 1 KiB, and `passes`, the number of passes over it. More of either
is never less secure; the limit is the time and memory the program can spend.

* hash gives libsodium's three presets: `argon2id_interactive`, 2 passes over
64 MiB, for a login; `argon2id_moderate`, 3 passes over 256 MiB, about 0.7 s
on libsodium's reference machine; `argon2id_sensitive`, 4 passes over 1 GiB,
about 3.5 s there, for keys that protect very sensitive data and are derived
rarely.
* To tune for a server, decide first how much memory one hash may take, given
how many logins run at once (ideally no more than one per core) and the
memory the machine is sure to have; set `memory` to it and `passes` to 3, and
time one hash. If it is too slow, lower the memory and keep 3 passes; if it is
fast enough, raise the passes. About one second is the most a login should
take; a desktop application that asks for its password once per session can
take about five; a job that runs rarely, such as restoring a backup, can take
longer.
* OWASP's minimum for a login is 19 MiB with 2 passes; libsodium's interactive
preset is above it.
* WebAssembly is slower than native (<<hash-measured>> has the measured times),
and a browser tab may not get a gigabyte: measure on the target.

*Pitfalls.*

* *A random 16-byte salt per password,* from `webcpp::crypto::random_device`;
`argon2id` refuses another size with `invalid_salt_size`.
* *Store the costs with the salt and the tag.* Verifying needs exactly the
same memory, passes and salt; a program that raises its costs later must know
which costs each stored tag used. hash has no `$argon2id$` string format:
the program stores the three values in its own record (<<hash-privacy-passwords>>).
* *Compare the tag with `webcpp::crypto::equal`.*
* *The memory is the backend's.* libsodium allocates the matrix with `mmap`
where there is one, else from the C heap; OpenSSL from its own allocator, the C
heap; both outside any allocator of the program (<<hash-backend-conditions>>).
`errc::not_enough_memory` reports a refusal.
* *Keep the password in memory briefly,* and overwrite it when done.
* *Not RFC 9106's other parameters.* Parallelism above 1, a secret (pepper) and
associated data are the family `argon2`'s (<<hash-argon2-family>>).

[#hash-argon2-family]
=== Every parameter of Argon2: `argon2`

`argon2<Variant>` is Argon2 with every parameter of RFC 9106, for the cases
the function `argon2id` does not cover: the variant, the passes, the memory,
the lanes (parallelism), a secret (a pepper, kept apart from the database, so
that a stolen database alone does not let an attacker test guesses) and
associated data, in an `argon2_parameters`. The variants are three:

* `kdfs::argon2id`, the hybrid, RFC 9106's and OWASP's first choice for
passwords. On libsodium it is the Argon2id of the function `argon2id`, with
the family's parameters.
* `kdfs::argon2i`, whose memory access does not depend on the password: an
attacker who watches the cache learns nothing of it, but with few passes an
attacker who keeps less memory pays less extra time than against Argon2id. It
is here to check tags a system already stored with it, such as those of
libsodium's `crypto_pwhash_argon2i`; new code takes Argon2id.
* `kdfs::argon2d`, whose memory access depends on the password: the best
against trade-offs between time and memory, but readable through side
channels. `backends::openssl` alone has it, and it has no default: the call
names the backend.

The default backend of Argon2id and Argon2i is libsodium (a program links
`/third_party//sodium`), which takes one lane, no secret and no associated
data, a 16-byte salt, a tag of 16 bytes or more, and for Argon2i 3 passes or
more. The family's guards are RFC 9106's; a value they accept that the backend
does not take is `unsupported_by_backend`, before any work, the output left as
it was. `backends::openssl` has every variant with every parameter, on
native, wasip2 and wasip3; it is never a default (design D34), so a call names
it.

*Pitfalls.*

* *Two units of memory.* `argon2_parameters::memory_kib` counts KiB, as
RFC 9106's m does; `argon2id_parameters::memory`, the parameter of `argon2id`,
counts bytes. The 268,435,456 bytes of `argon2id_moderate` are 262,144 KiB.
* *Every parameter changes the tag.* The lanes, the secret and the associated
data are inputs of the hash as the password and the salt are: verifying needs
all of them again, so a program stores the lanes with the costs, and keeps the
secret where it can read it again.
* *A value RFC 9106 allows may not be the backend's.* libsodium refuses four
lanes, a pepper, an 8-byte salt and a 4-byte tag with
`unsupported_by_backend`; check the error, and name a backend that takes the
value where one does.
* *Argon2i takes 3 passes or more on libsodium.* RFC 9106 allows 1 and 2,
which libsodium refuses with `unsupported_by_backend`: the attacks that trade
memory for time against Argon2i are cheapest with few passes.
* *Argon2d is not for passwords.* Its memory access depends on the password,
which a timing attacker on the same machine can read; Argon2id is the choice
for passwords.
* *Lanes are not threads.* OpenSSL computes the lanes one after the other, in
the calling thread (webcpp builds it without threads): four lanes give the
tag RFC 9106 defines for four lanes, in the time of four times the work, not a
quarter of it.
* *A secret is a pepper, not a salt.* It is the same for every password and
kept out of the database (in a key store or the program's configuration); the
salt stays random per password. Store neither with the tag.
* *OpenSSL's memory on wasm32.* m blocks of 1 KiB must fit a 32-bit `size_t`:
at most 4,194,303 KiB, `unsupported_by_backend` beyond; a WebAssembly runtime
may refuse far less, which `errc::not_enough_memory` reports.
* *The shortest tag.* RFC 9106 allows 4 bytes, which OpenSSL produces;
libsodium's shortest is 16. A password hash wants 16 or more.

[#hash-scrypt]
=== scrypt

scrypt (Percival, 2009; RFC 7914) was the first memory-hard password hash:
it fills a buffer of 128 r N bytes with Salsa20/8 and then reads it in an
order that depends on the data, so that an attacker without the memory
recomputes it again and again. Its costs are N (the memory and time, a power
of two), r (the block size) and p (the parallelism). Ethereum's keystore files
and many disk and backup encryption tools use it. libsodium, which hash runs,
recommends Argon2id unless a format demands scrypt. `scrypt` runs libsodium's by
default, and OpenSSL's where the call names `backends::openssl` (native, wasip2
and wasip3), with OpenSSL's own memory limit lifted:

*Choosing the costs.* OWASP's minimum is N 2^17^, r 8, p 1, which takes
128 MiB; libsodium's interactive costs are N 2^14^, r 8, p 1 (16 MiB), and it
advises never less than 16 MiB. Tune as for Argon2id: fix the memory the
program can spend, time one hash, then trade.

*Pitfalls.*

* *A random salt per password, the costs stored with the result,* and the
result compared with `webcpp::crypto::equal`, as for Argon2id.
* *libsodium's own limit:* N at most 4,294,967,295; hash refuses a larger one
with `invalid_parameters` on `backends::sodium`.
* *OpenSSL's own limits:* r p below 2^24^ (`invalid_parameters`), and a
password, salt or output of at most `INT_MAX` bytes (`input_too_long`,
`invalid_output_size`): its PBKDF2 takes these lengths as `int`s. OpenSSL
refuses by default a scrypt that needs more than 1,025 MiB; hash lifts that
limit, so that `backends::openssl` computes every cost libsodium does, as far
as the memory goes.
* *Memory on Emscripten.* The buffer grows the program's memory past
Emscripten's 16 MiB; `/third_party//sodium` links with
`-sALLOW_MEMORY_GROWTH=1` for it.
