[#hash-digests]
== Digests

A cryptographic digest is a fingerprint of data: a few dozen bytes that stand
for a file, a message or a block of a chain, such that changing any bit of the
data changes the fingerprint beyond recognition. It is what lets a
file-sharing app check that the file it received is the one it asked for, a
backup tool skip what it already stored, a wallet name a transaction, and a
signature sign a short value instead of a whole document. A digest has no key:
anybody can compute it, so it protects against accidents and against changes
made where the attacker cannot also replace the digest. Where the attacker can,
the answer is a MAC (<<hash-macs>>) or a signature.

Three properties make a hash cryptographic, each with its strength in bits:
collision resistance (nobody finds two inputs with the same digest; at best
half the digest's bits, by the birthday bound), preimage resistance (nobody
finds an input for a given digest) and second-preimage resistance (nobody
finds another input with the digest of a given one). A digest of 256 bits
gives 128-bit collision resistance, which no computer will reach; the
"Security" column below gives each function's.

[#hash-sha2]
=== SHA-2

SHA-2 is the family of digests NIST published in 2001 (FIPS 180-4 is its
current text): SHA-224 and SHA-256 over 32-bit words, SHA-384, SHA-512,
SHA-512/224 and SHA-512/256 over 64-bit words. SHA-256 is the most widely
deployed digest: TLS, Bitcoin, Git's new object format, Nostr and every
browser's WebCrypto have it, and recent x86 and Arm processors compute it in
hardware. Each is a Merkle-Damgård construction: the message, padded with its
length, is cut into blocks, and a compression function folds each block into a
state whose last value is the digest.

*Pitfalls.*

* *Length extension.* Whoever knows SHA-256(m) and the length of m can compute
SHA-256(m || padding || x) for any x without knowing m. So the digest of a key
followed by a message is not a MAC: an attacker appends to a signed request and computes
its valid "tag". Use HMAC (<<hash-hmac>>), or a digest that resists it:
SHA-384, SHA-512/256, SHA-3, BLAKE2 and BLAKE3.
* *A digest is not a password hash.* SHA-256 runs at hundreds of megabytes per
second; a stolen table of SHA-256 password digests is tested at billions of
guesses per second on a graphics card. Passwords go through Argon2id
(<<hash-argon2id>>).
* *A digest is compared as a public value.* Comparing two digests with `==` is
fine when both are public, a file's expected digest for example; a tag that
depends on a secret is compared with `webcpp::crypto::equal`
(<<hash-hmac>>).
* *Other backends, by name.* `backends::bearssl`, `backends::openssl` and
`backends::botan` compute SHA-2 too, never as a default: a call names one
(<<hash-digest-family>>). Botan has SHA-224, SHA-256, SHA-384, SHA-512 and
SHA-512/256, not SHA-512/224, natively and on Emscripten, with exceptions;
the bytes are the same on every backend.

[#hash-sha3]
=== SHA-3 and SHAKE

SHA-3 is the standard NIST chose by an open competition and published in 2015
as FIPS 202: the Keccak team's sponge. A sponge absorbs the message into a
large state of 1,600 bits, a block at a time, mixing it with the Keccak-p
permutation, then squeezes output from it. Its design shares nothing with
SHA-2, which is why it exists: if a weakness were found in SHA-2, SHA-3 would
not share it. It resists length extension by construction. SHA3-224 to
SHA3-512 have fixed digest sizes; SHAKE128 and SHAKE256 are extendable-output
functions (XOFs), which give as many bytes as the caller takes, and are what
NIST's post-quantum standards (ML-KEM, ML-DSA) use to expand seeds into
matrices.

*Pitfalls.*

* *An XOF's output length is the caller's security choice.* SHAKE128 gives at
most 128-bit security however much is taken, and a short output gives less:
16 bytes give only 64-bit collision resistance. Take what the protocol names.
* *Hash2's `result()` returns a whole block.* Each call of `result()` on
`shake_128` returns the next 168 bytes of the stream (136 for `shake_256`), as
Boost.Hash2 defines it; a program that wants bytes 32 to 63 takes them from
the first block, not from a second call.
* *SHA3-256 is not Keccak-256.* The padding differs (<<hash-keccak>>).
* *libsodium has SHA3-256, SHA3-512 and both SHAKEs too.* `digest_of` and
`hasher` reach them with `backends::sodium` named in the call (libsodium's
`crypto_hash_sha3256`, `crypto_hash_sha3512` and `crypto_xof_shake*`, every
output size), as they reach its SHA-256 and SHA-512 (<<hash-digest-family>>);
the bytes are the same on every backend. `backends::openssl` and
`backends::botan` have SHA3-224 to SHA3-512 and both SHAKEs, at every output
size, named in the call likewise.

[#hash-turboshake]
=== TurboSHAKE

TurboSHAKE128 and TurboSHAKE256 (RFC 9861, 2025, from the Keccak team) are
SHAKE128 and SHAKE256 with half the rounds: the same sponge over the same
1,600-bit state, its permutation run 12 rounds instead of 24, which makes
them roughly twice as fast with the same claimed security (128 and 256
bits; RFC 9861, sections 1 and 7). They are extendable-output functions, as
SHAKE is, and take one parameter more: a domain separation byte D, from 0x01
to 0x7F (0x1F by default), absorbed after the message, so that each value is
another function. A program that hashes several kinds of things gives each
kind its own byte, and a value of one kind never stands for a value of
another. TurboSHAKE is also the inner function of KangarooTwelve
(<<hash-kangarootwelve>>). `digest_of` and `hasher` take the byte in
`digest_options<digests::turboshake_128>` (or `_256`), on `backends::xkcp`,
their default, XKCP's own TurboSHAKE code, for which a program links
`/third_party//xkcp`; or on `backends::sodium`, libsodium's
`crypto_xof_turboshake128` and `crypto_xof_turboshake256`, named in the
call. Both give the same bytes.

*Pitfalls.*

* *TurboSHAKE is not SHAKE.* With 12 rounds instead of 24 it gives other
bytes for the same message: a format that names SHAKE128 needs SHAKE128
(<<hash-sha3>>).
* *The domain byte is part of the function.* Both sides of a protocol use
the same byte for the same purpose; a byte outside 0x01 to 0x7F is refused
(`invalid_parameters`) before any backend sees it, on every backend,
although libsodium would accept it and XKCP would take any byte but 0,
since RFC 9861 allows that range alone.
* *The output's length is the caller's security choice,* as for SHAKE: 32
bytes of TurboSHAKE128 give 128-bit security, 16 bytes give only 64-bit
collision resistance.

[#hash-kangarootwelve]
=== KangarooTwelve (KT128 and KT256)

KT128 and KT256 (RFC 9861) are KangarooTwelve, the Keccak team's fast hash
of large inputs: a tree over TurboSHAKE (<<hash-turboshake>>) that cuts its
input in chunks of 8,192 bytes, hashes each chunk on its own and hashes the
results, so that an implementation can hash a large file on several cores
or vector units, as ParallelHash does (<<hash-sp800-185>>), but faster and
with no block size to choose (RFC 9861, section 1). An input of up to
8,192 bytes is one TurboSHAKE call, so a short message costs little more.
Both are extendable-output functions with the security of SHAKE128 and
SHAKE256 (RFC 9861, section 7), and take a customisation string C, as
cSHAKE does: an application gives each of its uses its own string, and the
outputs are unrelated. They are tags of `digest_of` and `hasher`
(<<hash-digest-family>>), on `backends::xkcp`, their default: XKCP's own
KangarooTwelve code, which computes the chunks one after another. A
program links `/third_party//xkcp`.

*Pitfalls.*

* *A hasher reads C at `finish`.* KangarooTwelve absorbs the customisation
string after the message, and `hasher` keeps the span `make` took instead of
copying it (no allocation): the bytes stay alive and unchanged until
`finish`, or the digest is another one or the read is a dangling one.
`digest_of` reads C during the call.
* *C is part of the function.* KT128 with "app/v1" and KT128 with "app/v2"
are unrelated; an empty C is the RFC's default, and the 32-byte KT128 of a
message with no C is what IANA's "k12-256" names.
* *KT128 is not ParallelHash or BLAKE3.* Each tree hash gives its own
bytes: a format names one, and a file's KT128 never matches another's
ParallelHash128.
* *The output's length is the caller's security choice,* as for SHAKE:
32 bytes of KT128 give 128-bit security, 64 bytes of KT256 256-bit.
* *32-bit XKCP counts chunks in a `size_t`.* On wasm32 a message and C past
a little under 32 TiB together would wrap XKCP's count into a wrong digest;
they are refused (`input_too_long`) before XKCP sees them.

[#hash-keccak]
=== Keccak

Keccak-256 is Keccak as its authors submitted it to the SHA-3 competition,
before NIST changed the padding for FIPS 202. Ethereum adopted it before the
standard was final and kept it: an Ethereum address, a transaction id, a
Solidity function selector and the state trie are all Keccak-256. hash's
`keccak_256` runs XKCP's Keccak-p[1600] permutation (the Keccak team's own
code) under a sponge written line for line as Boost.Hash2's, so that it gives
Hash2's results for every sequence of calls (<<hash-departures>>,
<<hash-upstream>>). A program links `/third_party//xkcp`.

*Pitfalls.*

* *Keccak-256 is not SHA3-256.* The two differ in one padding byte, 0x01
against 0x06, and give unrelated digests. A library that offers "SHA3" for
Ethereum, or "Keccak" for a FIPS 202 format, computes a value nobody else
computes, and the mistake shows only as an address or a signature that does
not match. Use `keccak_256` exactly where a format says Keccak-256.

Keccak-224, Keccak-384 and Keccak-512, the submission's other sizes, are tags
of `digest_of` and `hasher` (<<hash-digest-family>>): `digests::keccak_224`,
`digests::keccak_384` and `digests::keccak_512`, on `backends::xkcp`, which
runs XKCP's FIPS 202 code (`Keccak_Hash`) with Keccak's padding, and on
`backends::openssl` when the call names it. The same XKCP backend, named in
the call, computes SHA3-224 to SHA3-512 and SHAKE128 and SHAKE256, any number
of bytes of SHAKE's stream; XKCP's own test vectors (the ShortMsgKAT files),
Boost.Hash2 and OpenSSL give the same values. `backends::botan` has
Keccak-224 to Keccak-512 too, named in the call (Botan's `Keccak-1600`, whose
module Botan 3.14.1 deprecates and still builds).

[#hash-sp800-185]
=== cSHAKE, TupleHash and ParallelHash (SP 800-185)

NIST SP 800-185 builds three hashes on SHAKE, each for a job a plain digest
does badly. *cSHAKE* is SHAKE with a customisation string: an application
that hashes the same data for two purposes, an identifier and a checksum,
gives each purpose its own string, and the two outputs are unrelated, so that
a value computed for one can never be passed off as the other. *TupleHash*
hashes a list of byte strings, a record's fields, so that the bounds between
them count: a signing app that hashes `name` then `amount` by plain
concatenation gives ("ab", "c") and ("a", "bc") the same digest, and an
attacker who controls one field can move bytes across the bound; TupleHash
encodes each field's length and cannot be fooled that way. *ParallelHash*
cuts a long input in blocks of B bytes, hashes each block on its own and
hashes the results, so that a large file can be hashed on several cores
(`backends::xkcp` computes the blocks one after another); the block size is
part of the function. All three come in a 128-bit and a 256-bit
strength (SP 800-185, section 8.1) and give any number of bytes; TupleHash and
ParallelHash have a fixed-length form, which encodes the output's length so
that their 32-byte and 64-byte digests are unrelated, and an XOF form, which
does not. They are tags of `digest_of` and `hasher`
(<<hash-digest-family>>), on `backends::xkcp`, their default: XKCP's own
SP 800-185 code. A program links `/third_party//xkcp`.

*Pitfalls.*

* *A TupleHash hasher takes one element per `update`.* Feeding a field in
two pieces makes two elements and another digest; `digest_of` hashes the
tuple of one element, its input. The empty tuple (no `update`) and the tuple
of one empty element differ.
* *The form is part of the digest.* TupleHash128 and TupleHashXOF128 of the
same input differ at every length, and so do the two forms of ParallelHash;
the fixed-length form's 32-byte digest is not the start of its 64-byte one.
Choose the form the format names, with `.xof`.
* *ParallelHash's block size has no default.* SP 800-185 leaves B to the
application, and a digest under another B is another digest: the call states
it (`.block_size`; 0 is `invalid_parameters`). XKCP takes a power of two of at
least 8 bytes and answers any other with `unsupported_by_backend`, NIST's
samples with B = 12 included; 8192 is common for large files.
* *The function name is NIST's.* cSHAKE's `function_name` is reserved for
functions NIST defines on it; an application separates its uses with
`customisation`. With both empty, cSHAKE is SHAKE.
* *Lengths in bits.* SP 800-185 counts every string in bits, which XKCP holds
in a `size_t`: on wasm32 a customisation, a TupleHash element, a
ParallelHash input (all its pieces together) or a fixed-length output past
512 MiB is refused (`input_too_long`, `invalid_output_size`) before XKCP sees
it, rather than hashed into a wrong digest.

[#hash-blake2]
=== BLAKE2

BLAKE2 (RFC 7693) is a digest faster than MD5 in software and as strong as
SHA-3, designed from BLAKE, a SHA-3 finalist. BLAKE2b works on 64-bit words
and gives up to 64 bytes; BLAKE2s works on 32-bit words, for small machines,
and gives up to 32 bytes. Both take a key, so a keyed BLAKE2 is a MAC without
HMAC's double pass (`macs::blake2b_mac` and `macs::blake2s_mac`,
<<hash-blake2b-mac-sodium>>). Argon2 is built on BLAKE2b, libsodium's generic hash is
BLAKE2b, and WireGuard uses BLAKE2s for its hash, its MAC and its HKDF.

*Pitfalls.*

* *The key goes to the constructor.* `blake2b_512(key, size)` is RFC 7693's

written into the message instead gives a different function, and a longer
key gives a function no other BLAKE2 implementation computes, so keep keys at
most 64 bytes (32 for BLAKE2s).
* *No salt, no personalisation, no variable length here.* RFC 7693's
parameter block also carries a salt, a personalisation string (16 bytes for
BLAKE2b, 8 for BLAKE2s) and the digest's length; Boost.Hash2's types fix them,
so a digest cut to 32 bytes is not BLAKE2b-256, which encodes its length in
its parameters. For BLAKE2b-256, or a salt or a personalisation, use
`digests::blake2b` (<<hash-blake2b-options>>).
* *Other backends, by name.* `digests::blake2s_256` is on `backends::hash2`,
its default, and on `backends::openssl` and `backends::botan`, named in the
call, the same bytes.

[#hash-blake2b-options]
=== BLAKE2b with a key, a salt, a personalisation and a length

RFC 7693 defines BLAKE2b with four parameters besides the message, each
written into the block that starts the hash, so that each choice is a
different function: the output's length (1 to 64 bytes), a key (up to 64
bytes, which makes it a MAC), a salt and a personalisation (16 bytes each).
`digest_of` and `hasher` over the tag `digests::blake2b` take all four in
`digest_options<digests::blake2b>`; the default backend, `backends::sodium`,
is libsodium's generic hash, `crypto_generichash`. A chat app that hashes
message ids, attachment ids and contact keys personalises each kind, so that
a value of one kind never stands for a value of another; a format such as
Zcash's transaction ids (https://zips.z.cash/zip-0244[ZIP 244]) names
BLAKE2b-256 with a personalisation of its own.

*Pitfalls.*

* *The length is a parameter, not a cut.* BLAKE2b-256 is not the first 32
bytes of BLAKE2b-512: the length goes in `output_size`, 64 by default, and
the output given to `digest_of` or `finish` has exactly that size
(`invalid_output_size` otherwise). A `hasher` takes it when it starts.
* *16 bytes or nothing.* A salt or a personalisation is 16 bytes or empty
(`invalid_salt_size`, `invalid_parameters`); pad a shorter name yourself, the
same way on every side, since the library does not guess a padding.
* *A key is a secret, the salt and personalisation are not.* For a MAC, use a
random key of 16 to 64 bytes from `webcpp::crypto::random_device`, compare
tags with `webcpp::crypto::equal`, and prefer `mac<macs::blake2b_mac>`
(<<hash-blake2b-mac-sodium>>); a key of 0 bytes is the unkeyed hash.
* *`backends::hash2` has BLAKE2b-512 alone.* Named in the call, it answers
`unsupported_by_backend` to a shorter output, a key, a salt or a
personalisation, rather than ignore one.
* *`backends::botan` has no salt or personalisation.* Named in the call, it
computes BLAKE2b at every length from 1 to 64 bytes, with a key or without
(Botan's `BLAKE2b(<bits>)`), and answers `unsupported_by_backend` to a salt or
a personalisation, which Botan's BLAKE2b does not take.

[#hash-blake3]
=== BLAKE3

BLAKE3 (2020) is one function with four uses: a digest, a keyed hash (a MAC),
a key derivation from a context string, and an extendable output. It splits
the input into chunks of 1 KiB, hashes them independently and joins them in a
binary tree, so it uses every SIMD lane of a processor and verifies a large
file in parts; its rounds are fewer than BLAKE2's. hash runs the official C
implementation, with its SIMD code natively and the portable code on
WebAssembly; a program links `/third_party//blake3`. In the measured data
(<<hash-measurements>>), BLAKE3 is the fastest cryptographic digest natively
on 1 MiB, and BLAKE2b is faster than BLAKE3 on wasip2, wasip3 and Emscripten.

* *A context names one purpose, forever.* BLAKE3's authors ask that a context

"example.com 2026-11-15 chat message keys": never a variable, never a secret.
The key material goes through `update`.
* *The seeded constructor is a keyed hash.* `blake3(seed_value)` and

* *`blake3` does not wipe itself.* Like Hash2's types, it holds the key in
its state until it is destroyed; a program that needs the key gone writes over
the object.

[#hash-legacy]
=== MD5, SHA-1 and RIPEMD: legacy

MD5 (1992) and SHA-1 (1995) are broken: collisions of MD5 are found in
seconds; the first public collision of SHA-1, an identical-prefix one,
https://shattered.io/[SHAttered], came in 2017, and the first public
chosen-prefix collision, two documents of the attacker's choosing with one
digest, https://sha-mbles.github.io/[SHA-1 is a Shambles], in 2019 (published
2020). RIPEMD-160 (1996) is not broken, but its 160 bits give 80-bit collision
resistance, below what new designs accept, and RIPEMD-128 gives 64. hash keeps
them because data and protocols use them: Git's original object ids, old
checksums, and Bitcoin's hash160, RIPEMD-160 over SHA-256, in every legacy and
SegWit v0 address (<<hash-crypto-hash160>>).

*Pitfalls.* Never choose one of them for a new design: a signature over an
MD5 or SHA-1 digest can be moved to a forged document. Read and check what
already exists; write SHA-256, SHA-3 or BLAKE3. HMAC over MD5 or SHA-1 is not
broken as a MAC, but it carries a broken name into audits; prefer
`hmac_sha2_256`. MD5-SHA1, the 36 bytes TLS 1.0 and 1.1 sign (MD5 of the
data, then SHA-1 of it; https://www.rfc-editor.org/rfc/rfc2246#section-4.7[RFC
2246, section 4.7]), is no stronger than SHA-1: `digests::md5_sha1` has no
default backend, and a program that must read old TLS data names

RIPEMD-160 are on `backends::openssl` and `backends::botan` too, named in the
call (Botan 3.14.1 deprecates its MD5 module and still builds it).

[#hash-md5-sha1]
=== MD5-SHA1: TLS 1.0's digest, on BearSSL or OpenSSL by name

MD5-SHA1 is the 36-byte digest that TLS 1.0 and 1.1 sign and check: the MD5
of the data followed by the SHA-1 of the same data
(https://www.rfc-editor.org/rfc/rfc2246#section-4.7[RFC 2246, section 4.7]).
Its designers paired the two so that a break of one would not break the pair;
https://doi.org/10.1007/978-3-540-28628-8_19[Joux showed in 2004] that a
collision of such a pair costs little more than a collision of its stronger
half, and https://www.mitls.org/pages/attacks/SLOTH[SLOTH] (2016) turned the
weakness into attacks on TLS. https://www.rfc-editor.org/rfc/rfc8996[RFC 8996]
deprecated TLS 1.0 and 1.1 in 2021. hash
has it because a program that reads, replays or tests old TLS data needs the
exact bytes: `digests::md5_sha1` is in BearSSL (`br_md5sha1_*`) and OpenSSL
(its "MD5-SHA1" digest) alone, so the call names `backends::bearssl` and the
program links `/third_party//bearssl`, or names `backends::openssl` and links
`/webcpp/hash//openssl`. No backend has an HMAC over it: no standard defines
one. The same naming reaches BearSSL's and OpenSSL's other digests and MACs,
which are never a default either.

*Pitfalls.*

* *Never for anything new.* Its 288 bits suggest a strength it does not

(<<hash-legacy>>). Write SHA-256.
* *No default.* `digest_of<digests::md5_sha1>` without a backend stops the

names the line to add.
* *The order is fixed.* MD5's 16 bytes come first, then SHA-1's 20: SHA-1
followed by MD5 is another value, which a TLS 1.0 peer rejects.

[#hash-sm3]
=== SM3: China's national digest

SM3 is the 256-bit digest of China's commercial cryptography standards,
published as GM/T 0004-2012 and as the national standard GB/T 32905-2016, and
in ISO/IEC 10118-3 since 2018. Its design follows SHA-256's (a Merkle-Damgard
chain over 512-bit blocks), with its own message expansion and compression.
A program needs it where a Chinese standard or regulator requires it: SM2
signatures hash with it, and
https://www.rfc-editor.org/rfc/rfc8998[RFC 8998] gives TLS 1.3 its ShangMi
cipher suites. Elsewhere SHA-256 is the interoperable choice. hash has it on
`backends::openssl`, OpenSSL 3.5.9's default provider, and on
`backends::botan`, Botan 3.14.1's `SM3`; it has no default backend, so the
call names one and the program links its library: `/webcpp/hash//openssl`
(native, wasip2 and wasip3; OpenSSL is not built for Emscripten) or
`/third_party//botan` (native and Emscripten, with exceptions).

[#hash-streebog]
=== Streebog

Streebog (GOST R 34.11-2012, https://www.rfc-editor.org/rfc/rfc6986[RFC
6986]) is Russia's national digest, which replaced GOST R 34.11-94 in 2013:
Streebog-256 and Streebog-512, a 512-bit state compressed block by block with
its own substitution, permutation and linear layers, and a checksum of the
message folded in at the end. Russian standards build on it: HMAC over it
and the key derivations of https://www.rfc-editor.org/rfc/rfc7836[RFC 7836],
the GOST signatures and the GOST cipher suites of TLS. Elsewhere SHA-256 and
SHA-512 are the interoperable choice. hash has it on `backends::botan`
alone, Botan 3.14.1's `Streebog-256` and `Streebog-512`: `digests::streebog_256`
and `digests::streebog_512` have no default backend, so the call names
`backends::botan`, and the program links `/third_party//botan`, natively or
on Emscripten, with exceptions (<<hash-jamfile>>).

This section adapts the warnings of Botan's documentation on Streebog
(`doc/api_ref/hash.rst` and `doc/deprecated.rst` of Botan 3.14.1, BSD-2-Clause
licence, kept in `NOTICE.md`), in hash's own terms.

*Pitfalls.*

* *Its S-box has a hidden structure.* Botan's documentation warns that
Streebog's S-box was shown to have a structure that interacts with its
linear layer in a way that may give a backdoor in some uses, and asks that
Streebog be avoided wherever possible; Botan 3.14.1 deprecates its module,

hashes and writes are those bytes reversed, as the example's are.

than Streebog-512: its digest is not the first half of the longer one.

[#hash-whirlpool]
=== Whirlpool

Whirlpool (Barreto and Rijmen, 2000) is a 512-bit digest built on a block
cipher close to AES, chosen by the NESSIE project in 2003 and standardised in
ISO/IEC 10118-3. Its use today is reading what was hashed with it: VeraCrypt
and TrueCrypt volumes derive their header keys with PBKDF2 over HMAC-Whirlpool
when the volume was made so, and some archives and file lists carry Whirlpool
checksums. hash has it on `backends::botan` alone (OpenSSL keeps it in its
legacy provider, which webcpp does not load): `digests::whirlpool` has no
default backend, so the call names `backends::botan` and the program links
`/third_party//botan`, natively or on Emscripten, with exceptions. Its
pitfalls adapt the warning of Botan's documentation on Whirlpool
(`doc/api_ref/hash.rst` of Botan 3.14.1, BSD-2-Clause licence, kept in
`NOTICE.md`).

*Pitfalls.*

* *Three versions, one name.* The digest of the first submission
(Whirlpool-0) and of its 2001 revision (Whirlpool-T) differ from the final
Whirlpool's, which ISO standardised and Botan computes: a checksum made by an
old tool may be one of the others.
* *Table lookups indexed by the data.* Botan's documentation warns that its
baseline Whirlpool indexes tables by the data, likely open to cache timing
attacks on secret data; its constant-time code needs AVX2 or AVX-512, which
webcpp's build of Botan does not load. HMAC-Whirlpool over a key, as
VeraCrypt's, runs that code too.
* *Slow and of another age.* Whirlpool is slower than SHA-512 and has no
hardware support; a new design takes SHA-512 or SHA3-512.

[#hash-skein]
=== Skein-512

Skein (Ferguson, Lucks, Schneier and others, 2008) is a finalist of the SHA-3
competition, built on Threefish, a tweakable block cipher of additions,
rotations and XORs that is fast on 64-bit processors. Skein-512 has a 512-bit
state and gives any length of output; `digests::skein_512` is Skein-512 with
its 64-byte digest, Skein 1.3, the version of the competition's last round.
Keccak won, and Skein remains where a format chose it before. hash has it on `backends::botan` alone, Botan's
`Skein-512(512)`, with no default: the call names `backends::botan` and the
program links `/third_party//botan`, natively or on Emscripten, with
exceptions.

[#hash-digest-family]
=== One call, or pieces with one result: `digest_of` and `hasher`

The types above are Boost.Hash2's form: an object fed with `update` whose
`result()` can be called again, and which `hash_append` and the rest of
Boost.Hash2 take. Two functions reach the same algorithms through a tag of
`webcpp::hash::digests`, as `digests::sha2_256`, and a backend: `digest_of`
hashes a message in one call, and `hasher` takes it in pieces, as a file read
in blocks or a stream arrives, and gives exactly one result. The backend is the
tag's default, the first of `backends::hash2`, `backends::xkcp`,
`backends::blake3` and `backends::sodium` that has it, or the one the call
names as its second template argument; the tables of each algorithm list them.

*Pitfalls.*

* *One result.* A `hasher` gives its result once: a second `finish`, or an
`update` after it, is `error::invalid_state`, not the hash of what came
before; start another hasher for another message. A hasher is move-only, and
wipes its state when it finishes, when it is destroyed and when it is moved
from.
* *The output's size is the digest's.* A fixed-size digest takes an output of
exactly its size (`invalid_output_size` otherwise, the output untouched); an
extendable-output function, SHAKE or BLAKE3, takes any size from 1 byte;
BLAKE2b takes the size its options name (<<hash-blake2b-options>>).
* *A backend may have a tag in part.* `backends::hash2` has BLAKE2b with its
64-byte output and no option alone, and answers `unsupported_by_backend` to a
shorter output or to an option; `backends::openssl` has BLAKE2b unkeyed, at
every output size, with no key, salt or personalisation. A call that names a
backend gets what that backend has, which its row of the tables says.
* *Some backends are reached only by name.* `backends::bearssl` and
`backends::openssl` are never a default. BearSSL's MD5, SHA-1, SHA-2 and
SHAKE (any output size) run only when the call names it, as
`digest_of<digests::sha2_256, backends::bearssl>`, and the program links
`/third_party//bearssl`; OpenSSL's MD5, SHA-1, SHA-2, SHA-3, SHAKE (any output
size), Keccak, BLAKE2, RIPEMD-160, MD5-SHA1 and SM3 likewise, with
`/webcpp/hash//openssl`. `backends::botan` is reached by name too, in a
program built with exceptions that links `/third_party//botan`: its MD5,
SHA-1, SHA-2, SHA-3, SHAKE, Keccak, BLAKE2, RIPEMD-160 and SM3, and Streebog,
Whirlpool and Skein-512, which no other backend has (<<hash-streebog>>,
<<hash-whirlpool>>, <<hash-skein>>). `digests::md5_sha1` is in BearSSL and
OpenSSL alone and has no default (<<hash-md5-sha1>>). OpenSSL's SHA-256/192 (SHA-256's
first 24 bytes) and its KMAC hash have no tag, and Whirlpool is in OpenSSL's
legacy provider, which webcpp does not load: the capability table says why.
* *A tag without its backend stops the build.* A tag whose backend the
program does not link stops with a message that names the line to add; a tag
that the backend does not have stops with a message that names the backends
that have it, or says that none has it (<<hash-jamfile-messages>>).
