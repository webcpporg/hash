[#hash-kdfs]
== Key derivation

A key derivation function (KDF) turns secret material that is not fit to be a
key, or is fit to be one key only, into as many keys as an application needs.
Two people who agree on a shared secret by Diffie-Hellman get a point of an
elliptic curve, whose bytes are not uniformly random; a password manager has
one master key and needs a key per vault, per device, per purpose. Using the
same key for two purposes, encryption and authentication for example, can let
an attack on one break the other; using a raw Diffie-Hellman output as an AES
key wastes part of its strength. HKDF fixes both: it concentrates the entropy
of its input into a pseudorandom key, then expands it into independent keys,
one per label. BLAKE2b subkeys, libsodium's `crypto_kdf`, split a master key
that is already uniformly random into keys numbered by id. PBKDF2 is the older
answer to another problem, a key from a password, which Argon2id now answers
better (<<hash-password-hashing>>).

The key derivations are the functions of hash that run on a backend, a C
library or Boost.Hash2, that the program names or leaves to the default,
`backends::hash2` (<<hash-default-backend>>); BLAKE2b subkeys run on libsodium
alone. Each backend gives the same bytes for the same inputs: the
tests check them against each other on random inputs on every target.

[#hash-hkdf]
=== HKDF

HKDF (RFC 5869, 2010, Krawczyk) has two steps, both HMACs. *Extract* takes an
optional salt and the input keying material (IKM) and returns a pseudorandom
key (PRK) of the hmac's digest size: `PRK = HMAC(salt, IKM)`. *Expand* takes
the PRK and an info string, the label of one purpose, and returns up to 255
digests of output, each block an HMAC of the previous block, the info and a
counter. `hkdf` does both; `hkdf_extract` and `hkdf_expand` do one each, for
a protocol that names a step, or a program that extracts once and expands
many times. TLS 1.3, Signal, WireGuard, Noise and Nostr's NIP-44 derive their
keys with it.

This section adapts the guidance of libsodium's documentation on HKDF
(`key_derivation/hkdf.md` of
https://github.com/jedisct1/libsodium-doc[libsodium-doc], ISC licence, kept in

*Choosing the inputs.*

* *IKM* is the secret. It may be non-uniform (a Diffie-Hellman result) but
must hold enough entropy: extract concentrates entropy, it never adds any. A
password has too little; it goes through Argon2id.
* *Salt* is optional and public: a random value per session, or a constant
that names the application or the protocol (NIP-44 uses `nip44-v2`). It
separates the keys of different applications that might share a secret. An
empty salt is RFC 5869's string of zeros, and fine when the IKM is never
reused across applications.
* *Info* names the purpose and is public. Each key gets its own info, written
so that no two purposes can produce the same string: an application name, a
version and the purpose, as `example chat v1 encryption`. Info is limited to
32,768 bytes on every backend.
* *PRK* must stay secret, and `hkdf_expand` takes one of exactly the digest's
size (`invalid_key_size` otherwise). A key that is already uniform and of
that size, such as 32 bytes from `webcpp::crypto::random_device`, can be
expanded without the extract step.
* *HMAC-SHA-256 is the usual choice.* HMAC-SHA-512 gives longer blocks and no
practical gain in security; use it when a protocol names it.

*Pitfalls.*

* *Never HKDF for a password.* HKDF is fast by design: a key derived from a
password with HKDF is guessed as fast as the password's digest.
* *One info, one purpose.* Two keys derived with the same IKM, salt and info
are the same key.
* *The output is limited:* 255 times the digest size, 8,160 bytes over
HMAC-SHA-256; more fails with `invalid_output_size`, the output untouched.

[#hash-kdfs-backends]
=== Naming a backend

Most programs never name a backend: the call takes the default,
`backends::hash2`, on every target (<<hash-default-backend>>). A program names
one as the call's second template argument, to match the bytes
of another program exactly, to share a C library the program already links, or to test one backend
against another. `backend_has_v<Backend, Kdf, Hmac>` says at compile time
whether a backend has a function over an hmac; a call on a backend that does
not stops the build with a message that names the backends that do.

[#hash-pbkdf2]
=== PBKDF2

PBKDF2 (RFC 8018, first published in 2000 in PKCS #5 v2.0) derives a key from
a password by iterating an HMAC: each block of output is the XOR of thousands
or millions of chained HMACs of the password, so that every guess an attacker
tries costs as many HMACs as the iteration count. It needs no memory, which
is its weakness: a graphics card or a dedicated chip runs thousands of PBKDF2
guesses in parallel, where Argon2id and scrypt force each guess to hold
megabytes. PBKDF2 remains where a standard names it: BIP39 derives every
Bitcoin wallet's seed from its words with 2,048 iterations of HMAC-SHA-512,
and FIPS 140 validated products accept it when Argon2id is not approved.

*Pitfalls.*

* *Iterations are the whole defence.* OWASP's Password Storage Cheat Sheet
recommends 600,000 iterations of HMAC-SHA-256, or 210,000 of HMAC-SHA-512, for
passwords; BIP39's 2,048 protect a seed of high entropy, not a password.
Measure the time on the slowest device the program runs on (a phone, a
browser tab: WebAssembly is slower than native; <<hash-measured>> has the
measured times).
* *A random salt per password,* 16 bytes from `webcpp::crypto::random_device`,
stored beside the result: without it, one guess tests every user at once and
precomputed tables work.
* *Ask for no more than one digest.* Each further block of output costs the
defender the full iteration count again, and the attacker, who checks the
first block alone, nothing.
* *Prefer Argon2id for a new design* (<<hash-argon2id>>).

[#hash-blake2b-subkey]
=== BLAKE2b subkeys

`blake2b_subkey` derives many keys from one master key, each named by a number,
the subkey's id, and an 8-byte context that names the application or the part
of it, as libsodium's `crypto_kdf_derive_from_key` does. A chat app keeps one
32-byte master key and asks for subkey 1 to encrypt messages and subkey 2 to
authenticate them; a backup tool asks for one subkey per archive. A subkey is
BLAKE2b (RFC 7693) of the empty message, keyed with the master key, with the
id in BLAKE2b's salt and the context in its personalisation: one fast call,
and the bytes a libsodium program derives from the same master key, id and
context. It runs on `backends::sodium` (`/third_party//sodium`), the one
backend that has it.

Unlike HKDF, it does not extract: the master key must already be 32 uniformly
random bytes, from `webcpp::crypto::random_device` or from another KDF. A
Diffie-Hellman result or a password goes through HKDF or Argon2id first.

*Pitfalls.*

* *The master key is random, never a password.* `blake2b_subkey` adds no
work per guess: from a password, derive the master key with Argon2id
(<<hash-argon2id>>) first.
* *The context is exactly 8 bytes.* A shorter or a longer one is
`invalid_parameters`, never padded or cut, so that two programs cannot
disagree on its bytes; spell it as a constant of 8 characters, as
`"vault v1"`.
* *One id, one purpose.* The same id and context always give the same key:
keep the ids in one list, and never reuse one for a second purpose.
* *The length is part of the key.* A subkey of 16 bytes is not the first half
of the one of 32 with the same id: BLAKE2b's output size is a parameter of the
hash. Lengths of 16 to 64 bytes are accepted, others are
`invalid_output_size`.
