[#hash-kdfs]
== Key derivation

A key derivation function (KDF) turns secret material that is not fit to be a
key, or is fit to be one key only, into as many keys as an application needs.
Two people who agree on a shared secret by Diffie-Hellman get a point of an
elliptic curve, whose bytes are not uniformly random; a password manager has
one master key and needs a key per vault, per device, per purpose. Using the
same key for two purposes, encryption and authentication for example, can let
an attack on one break the other; using a raw Diffie-Hellman output as an AES
key wastes part of its strength. HKDF fixes both: it concentrates the entropy
of its input into a pseudorandom key, then expands it into independent keys,
one per label. BLAKE2b subkeys, libsodium's `crypto_kdf`, split a master key
that is already uniformly random into keys numbered by id. PBKDF2 is the older
answer to another problem, a key from a password, which Argon2id now answers
better (<<hash-password-hashing>>). Standards and formats that predate HKDF,
or were written for NIST's validations, name their own derivations: Kerberos
and NIST SP 800-108's KBKDF, JOSE's ECDH-ES and NIST SP 800-56C's one-step KDF,
ECIES and ANSI X9.63's KDF (<<hash-kdf-standards>>).

The key derivations are the functions of hash that run on a backend, a C
library or Boost.Hash2, that the program names or leaves to the default,
`backends::hash2` (<<hash-default-backend>>); BLAKE2b subkeys run on libsodium
alone, and the key derivations of standards on OpenSSL or Botan, which are
never a default: the call names one (<<hash-kdfs-botan>>). Each backend gives
the same bytes for the same inputs: the tests check them against each other on
random inputs on every target.

Every key derivation computes on a secret, and sets DIT (data-independent
timing) around each call, on every synchronous backend, on 64-bit ARM under
Apple's systems and Linux where the CPU has FEAT_DIT, leaving the thread's DIT
as it found it (<<hash-backends-dit>>): `hkdf_extract`, `hkdf_expand`, `hkdf`
(each also over byte pieces), `pbkdf2`, `blake2b_subkey`, `kbkdf`, `sskdf` and
`x963kdf`. `hkdf` enters one guard and runs the whole derivation inside it, and
HKDF and PBKDF2 on `backends::hash2` run Boost.Hash2's `hmac` there too.

[#hash-hkdf]
=== HKDF

HKDF (RFC 5869, 2010, Krawczyk) has two steps, both HMACs. *Extract* takes an
optional `salt` and the `input_key_material` (RFC 5869's IKM) and returns a
`pseudorandom_key` (the PRK) of the hmac's digest size:
`PRK = HMAC(salt, IKM)`. *Expand* takes the `pseudorandom_key` and the
`application_info` (RFC 5869's info), the label of one purpose, and returns up
to 255 digests of `output_key_material`, each block an HMAC of the previous
block, the info and a counter. `hkdf` does both; `hkdf_extract` and
`hkdf_expand` do one each, for a protocol that names a step, or a program that
extracts once and expands many times. TLS 1.3, Signal, WireGuard, Noise and
Nostr's NIP-44 derive their keys with it.

This section adapts the guidance of libsodium's documentation on HKDF
(`key_derivation/hkdf.md` of
https://github.com/jedisct1/libsodium-doc[libsodium-doc], ISC licence, kept in
`NOTICE.md`), in hash's own terms.

*Choosing the inputs.*

* *`input_key_material`* is the secret. It may be non-uniform (a
Diffie-Hellman result) but must hold enough entropy: extract concentrates
entropy, it never adds any. A password has too little; it goes through
Argon2id.
* *`salt`* is optional and public: a random value per session, or a constant
that names the application or the protocol (NIP-44 uses `nip44-v2`). It
separates the keys of different applications that might share a secret. An
empty salt is RFC 5869's string of zeros, and fine when the IKM is never
reused across applications.
* *`application_info`* names the purpose and is public. Each key gets its own
info, written so that no two purposes can produce the same string: an
application name, a version and the purpose, as `example chat v1 encryption`.
The info of a single buffer is limited to `hkdf_max_application_info_size`,
32,768 bytes, on every backend (1,024 in WebCrypto's `async_hkdf`,
<<hash-async-webcrypto>>); the forms over pieces take any length
(<<hash-hkdf-pieces>>).
* *`pseudorandom_key`* must stay secret, and `hkdf_expand` takes one of
exactly the digest's size (`invalid_key_size` otherwise). A key that is
already uniform and of that size, such as 32 bytes from
`webcpp::crypto::random_device`, can be expanded without the extract step.
* *HMAC-SHA-256 is the usual choice.* HMAC-SHA-512 gives longer blocks and no
practical gain in security; use it when a protocol names it.

*Pitfalls.*

* *Never HKDF for a password.* HKDF is fast by design: a key derived from a
password with HKDF is guessed as fast as the password's digest.
* *One info, one purpose.* Two keys derived with the same IKM, salt and info
are the same key.
* *The output is limited:* 255 times the digest size, 8,160 bytes over
HMAC-SHA-256; more fails with `invalid_output_size`, the output untouched.

=== Naming a backend

Most programs never name a backend: the call takes the default,
`backends::hash2`, on every target (<<hash-default-backend>>). A program names
one as the call's second template argument, to match the bytes of another

[#hash-hkdf-pieces]
=== HKDF over pieces

Protocols seldom give HKDF one buffer. HPKE (RFC 9180) extracts from
`HPKE-v1`, the suite's identifier, a label and the secret, one after another;
TLS 1.3's `HKDF-Expand-Label` builds its info from a length, a label and a
context. Joining the parts takes a buffer: on the heap, with a copy of the
secret to wipe afterwards, or on the stack, with a size that someone must
bound. `hkdf_extract`, `hkdf_expand` and `hkdf` each have a form over
`byte_pieces` (`<webcpp/hash/byte_pieces.hpp>`, which
`<webcpp/hash/hkdf.hpp>` includes) that takes the input keying material and
the application info as a list of spans, read one after another as if joined,
and feeds each piece to the backend's HMAC: no buffer, no copy of the secret.

* `hkdf_extract<Hmac, Backend>(salt, input_key_material)`
* `hkdf_expand<Hmac, Backend>(output_key_material, pseudorandom_key, application_info)`
* `hkdf<Hmac, Backend>(output_key_material, salt, input_key_material, application_info)`

The salt and the pseudorandom key stay one span each. The bytes are those of
the single-buffer form over the parts joined: the tests check them against
each other on random inputs and random splits on every backend.

*No cap, no heap.* The forms over pieces refuse only what RFC 5869 refuses: an
output of 0 bytes or of more than 255 digests (`invalid_output_size`), and for
`hkdf_expand` a pseudorandom key of another size than the digest's
(`invalid_key_size`); then the limits of the backend's HMAC key (OpenSSL takes
a salt of at most `INT_MAX` bytes, `input_too_long` beyond). The input keying
material, the application info and the number of pieces have no limit:
`hkdf_max_application_info_size` belongs to the single-buffer forms alone. A
piece longer than the backend's length type holds is fed in slices. On
`backends::hash2`, `backends::sodium` and `backends::bearssl` hash allocates
nothing, whatever the number and the size of the pieces (test `allocation`);
OpenSSL's and Botan's allocations are theirs, counted in <<hash-allocation>>.
Every HMAC state, every block and the pseudorandom key between the two steps
are wiped, on success and on failure.

*Writing the pieces.*

* *A braced list at the call,* `{a, b, c}`: each element converts to
`std::span<std::uint8_t const>` (a `std::array`, a `std::vector`, a span). Its
array lives until the end of the call's full expression, after the call
returns.
* *One piece is `+byte_pieces{x}+`.* A braced list of one span, `+{x}+`, is that
span (the language's rule), so `+hkdf_expand(okm, prk, {info})+` calls the
single-buffer form, with its limit; `+hkdf_expand(okm, prk, byte_pieces{info})+`
calls the form over pieces. `hkdf` takes both inputs as pieces or both as
spans: beside a list, one buffer is written `+byte_pieces{input_key_material}+`.
* *`{}` and `+{x}+` of another type do not compile.* Where both forms take
braces, a lone `{}`, or a braced list of one element that is not exactly a
`std::span<std::uint8_t const>` (`+{vec}+`, `+{array}+`), matches both forms and
the call is ambiguous: `hkdf(okm, salt, {}, {})` and `hkdf(okm, {}, {}, {})`,
which compiled before the forms over pieces existed, no longer do. Pass `x`
itself, an empty `std::span<std::uint8_t const>`, or `+byte_pieces{...}+`
(`byte_pieces{}` for no piece). The asynchronous forms follow the same rule
(<<hash-async-cheap>>).
* *A list kept in a variable is a `std::array` of spans,* as
`std::array<std::span<std::uint8_t const>, 3> const parts{prefix, label, secret};`,
passed as it is (a `std::vector` or a span of spans too); never a
`byte_pieces` variable. `byte_pieces parts{a, b};` points to its braced list's
array, which dies at the end of the declaration; where the compiler has the
`lifetimebound` attribute, it warns.

[#hash-pbkdf2]
=== PBKDF2

PBKDF2 (RFC 8018, first published in 2000 in PKCS #5 v2.0) derives a key from
a password by iterating an HMAC: each block of output is the XOR of thousands
or millions of chained HMACs of the password, so that every guess an attacker
tries costs as many HMACs as the iteration count. It needs no memory, which
is its weakness: a graphics card or a dedicated chip runs thousands of PBKDF2
guesses in parallel, where Argon2id and scrypt force each guess to hold
megabytes. PBKDF2 remains where a standard names it: BIP39 derives every
Bitcoin wallet's seed from its words with 2,048 iterations of HMAC-SHA-512,
and FIPS 140 validated products accept it when Argon2id is not approved.

*Pitfalls.*

* *Iterations are the whole defence.* OWASP's Password Storage Cheat Sheet
recommends 600,000 iterations of HMAC-SHA-256, or 210,000 of HMAC-SHA-512, for
passwords; BIP39's 2,048 protect a seed of high entropy, not a password.
Measure the time on the slowest device the program runs on (a phone, a
browser tab: WebAssembly is slower than native; <<hash-measured>> has the
measured times).
* *A random salt per password,* 16 bytes from `webcpp::crypto::random_device`,
stored beside the result: without it, one guess tests every user at once and
precomputed tables work.
* *Ask for no more than one digest.* Each further block of output costs the
defender the full iteration count again, and the attacker, who checks the
first block alone, nothing.
* *Prefer Argon2id for a new design* (<<hash-argon2id>>).

[#hash-blake2b-subkey]
=== BLAKE2b subkeys

`blake2b_subkey` derives many keys from one master key, each named by a number,
the subkey's id, and an 8-byte context that names the application or the part
of it, as libsodium's `crypto_kdf_derive_from_key` does. A chat app keeps one
32-byte master key and asks for subkey 1 to encrypt messages and subkey 2 to
authenticate them; a backup tool asks for one subkey per archive. A subkey is
BLAKE2b (RFC 7693) of the empty message, keyed with the master key, with the
id in BLAKE2b's salt and the context in its personalisation: one fast call,
and the bytes a libsodium program derives from the same master key, id and
context. It runs on `backends::sodium` (`/third_party//sodium`), the one
backend that has it.

Unlike HKDF, it does not extract: the master key must already be 32 uniformly
random bytes, from `webcpp::crypto::random_device` or from another KDF. A
Diffie-Hellman result or a password goes through HKDF or Argon2id first.

*Pitfalls.*

* *The master key is random, never a password.* `blake2b_subkey` adds no
work per guess: from a password, derive the master key with Argon2id
(<<hash-argon2id>>) first.
* *The context is exactly 8 bytes.* A shorter or a longer one is
`invalid_parameters`, never padded or cut, so that two programs cannot
disagree on its bytes; spell it as a constant of 8 characters, as
`"vault v1"`.
* *One id, one purpose.* The same id and context always give the same key:
keep the ids in one list, and never reuse one for a second purpose.
* *The length is part of the key.* A subkey of 16 bytes is not the first half
of the one of 32 with the same id: BLAKE2b's output size is a parameter of the
hash. Lengths of 16 to 64 bytes are accepted, others are
`invalid_output_size`.

[#hash-kdf-standards]
=== Key derivations of standards

Three key derivations are here because a standard, a protocol or a device
names them, and a program that talks to it must derive the same bytes: a
Kerberos client, a JSON Web Encryption library, an ECIES implementation, a
smart card's secure channel. Each repeats a hash or an HMAC with a counter,
block after block, over the secret and a description of the key, as HKDF's
expand step does; none of them extracts first, so the secret must already be
a key or a key agreement's shared secret, never a password. For a new design
HKDF is the better choice (<<hash-hkdf>>): it is as fast, it extracts, and
WebCrypto and every library have it.

They run on `backends::openssl` (OpenSSL 3.5.9's `EVP_KDF` implementations
"KBKDF", "SSKDF" and "X963KDF"), which a program names in the call and links
as `/webcpp/hash//openssl`, on native, wasip2 and wasip3; and on
`backends::botan` (Botan 3.14.1's `SP800-108-Counter`, `SP800-56A` and
`KDF2`), named likewise and linked as `/third_party//botan`, natively and on
Emscripten, with exceptions (<<hash-kdfs-botan>>). None of them has a default
backend (<<hash-default-backend>>), and a call that names none stops the build
with "... has no default backend. Name one of: backends::openssl,
backends::botan.".
The tests check each against OpenSSL's own test files, NIST's validation
vectors among them, Botan's own, and a second implementation over
Boost.Hash2.

[#hash-kbkdf]
==== KBKDF (NIST SP 800-108)

`kbkdf` is NIST SP 800-108's key-based key derivation in counter mode over an
HMAC: from a key-derivation key K~IN~, each block of output is
`HMAC(K_IN, [i] || Label || 0x00 || Context || [L])`, the counter i written in
r bits (32 by default), L the output's length in bits. The *label* names what
the derived key is for and the *context* who or what it belongs to (the
parties, a session). Kerberos's AES-SHA2 encryption types (RFC 8009) derive
their keys this way, and so do validated modules that must use an approved
derivation from a key. `kbkdf_options` sets the label and the context, and
can leave out the separator, L or both and narrow the counter to 8, 16 or 24
bits, for a format that fixes another form of the fixed input; NIST's
validation vectors pass their whole fixed input as the context, with neither.

*Pitfalls.*

* *Match every knob of the other side.* The counter's width, the separator and
L change every byte of the output: a key derived with L is not the key
derived without it. Read the format's definition, and check one of its test
vectors, as the example does with RFC 8009's.
* *The output's length is part of the key* when L is in the fixed input (the
default): 16 bytes are not the first half of 32.
* *The key is a key.* A password goes through Argon2id first
(<<hash-argon2id>>); `kbkdf` adds no work per guess. An empty key is
`invalid_key_size`.
* *Approval is the hash's.* SP 800-108 approves HMAC over SHA-1, SHA-2 or
SHA-3. `kbkdf` also takes HMAC over MD5, RIPEMD-160 or BLAKE2, for the formats
that use them, and does not stop the build as `sskdf` and `x963kdf` do: where
an approved derivation is required, pick SHA-2 or SHA-3.
* *Its limits:* at most 2^r^ - 1 blocks, and with L at most 536,870,911 bytes
(L counts bits in 32 of them), `invalid_output_size` otherwise; a counter of
another width than 8, 16, 24 or 32 bits is `invalid_parameters`; OpenSSL takes
an HMAC key of at most `INT_MAX` bytes (`unsupported_by_backend`).
* *Botan writes the separator and L, always.* `backends::botan` computes
SP 800-108's default fixed input alone, with the separator and a 32-bit L:
`kbkdf_options` with `.separator = false` or `.length = false` is
`unsupported_by_backend` there: NIST's validation vectors, written without
either, therefore cannot run on Botan (<<hash-kdfs-botan>>).

[#hash-sskdf]
==== One-step KDF (NIST SP 800-56C)

`sskdf` is the one-step key derivation of NIST SP 800-56C over a hash, the
"Concat KDF" of SP 800-56A: each block is `H(counter || Z || FixedInfo)`, the
counter 32 bits from 1, Z the shared secret of a key agreement (an ECDH
result) and FixedInfo the description of the key both parties write the same
way. JOSE's ECDH-ES, the key agreement of JSON Web Encryption (RFC 7518), and
Kerberos's PKINIT (RFC 8636) derive their keys with it. It takes SHA-1, a
SHA-2 or a SHA-3 (`digests::sha1` to `digests::sha3_512`), the hash functions
SP 800-56C approves; another digest stops the build.

*Pitfalls.*

* *FixedInfo is the protocol's, byte for byte.* JOSE writes each field as its
length in 4 bytes and its bytes, and ends with the key's length in bits: the
same fields in another form give another key. Check one of the protocol's
examples, as this one does with RFC 7518's.
* *Z is the raw shared secret,* the x-coordinate of the ECDH result, not a
hash of it: an empty one is `invalid_key_size`.
* *Its limits:* at most 2^32^ - 1 blocks (`invalid_output_size`) and the input
the hash takes (`input_too_long`, past 2^61^ bytes for SHA-1 and SHA-256);
OpenSSL takes a secret, a FixedInfo and an output of at most 2^30^ bytes each
(`unsupported_by_backend`). `backends::botan` has no SHA-512/224: `sskdf`
over it on Botan stops the build, naming `backends::openssl`.

[#hash-x963kdf]
==== X9.63 KDF (ANSI X9.63, SEC 1)

`x963kdf` is the key derivation of ANSI X9.63, which SEC 1 specifies for
ECIES and for elliptic-curve key agreement: each block is
`H(Z || counter || SharedInfo)`, the same as SP 800-56C's but with the
counter after the shared secret, so the two never give the same bytes. An
ECIES implementation derives the encryption key and the MAC key of a message
from the ECDH result with it, in one derivation cut in two; smart cards and
the key agreements of BSI TR-03111 use it too. It takes SHA-1, SHA-224,
SHA-256, SHA-384 or SHA-512, the hash functions SEC 1 lists (section 3.5) and
NIST SP 800-135 approves for it (FIPS 180-3's); SHA-512/224, SHA-512/256,
SHA-3 or another digest stops the build.

*Pitfalls.*

* *SharedInfo is the scheme's.* ECIES variants differ in what they put there

* *Not interchangeable with `sskdf`:* the counter's place differs, and so does
every byte.
* *Its limits:* fewer bytes than 2^32^ - 1 blocks (`invalid_output_size`) and
the input the hash takes (`input_too_long`); OpenSSL takes a secret, a
SharedInfo and an output of at most 2^30^ bytes each
(`unsupported_by_backend`); Botan's KDF2 derives at most 2^32^ - 2 blocks, one
fewer than ANSI X9.63 allows (`unsupported_by_backend` for the last). An empty
secret is `invalid_key_size`.

[#hash-kdfs-botan]
=== Key derivation on Botan

`backends::botan` computes HKDF, PBKDF2 and the three key derivations of
standards through Botan 3.14.1's `KDF` and `PasswordHashFamily`, natively and
on Emscripten, in a program built with exceptions that links
`/third_party//botan`. It is never a default (design D34): a call names it,
as the second template argument, `hkdf<hmac_sha2_256, backends::botan>`. Its
HKDF (extract, expand and both), PBKDF2 and KBKDF take every hmac of
`hmac.hpp` but `hmac_ripemd_128` and `hmac_sha2_512_224`, whose digests Botan
does not have; its one-step KDF (`SP800-56A`) takes the digests SP 800-56C
approves but SHA-512/224, and its X9.63 KDF (`KDF2`) the five SEC 1 lists. A
call over another stops the build with a message that names the backends that
have it. The tests check Botan against the RFCs' vectors, Botan's own test
files and every other backend, on random inputs.

*Pitfalls.*

* *KBKDF's fixed input is SP 800-108's default, always.* Botan writes the
separator and L (32 bits) whatever `kbkdf_options` says, so `.separator =
false` or `.length = false` is `unsupported_by_backend` there; a format that
leaves either out names `backends::openssl` (<<hash-kbkdf>>).
* *One block short of the standards.* Botan's PBKDF2 and KDF2 derive at most
2^32^ - 2 blocks, where RFC 8018 and ANSI X9.63 allow 2^32^ - 1: PBKDF2's
last block is `invalid_output_size`, X9.63's `unsupported_by_backend`, before
Botan is called. No program asks for 128 GiB of a key.
* *An iteration count in a `size_t`.* On Emscripten (wasm32) Botan's PBKDF2
takes at most 2^32^ - 1 iterations: more is `invalid_iterations`.
* *Long HMAC keys are hashed first.* Botan's HMAC takes a key of at most
8,192 bytes; hash hashes a longer one first (an HKDF salt, a PBKDF2 password,
a KBKDF key), as RFC 2104 does, so the bytes are every other backend's.
* *Botan allocates and throws.* Each call makes Botan's objects with
`operator new` and their secret buffers with `calloc`, overwritten and freed
before it returns; an exception is caught at
the call's boundary, `errc::not_enough_memory` for an allocation,
`backend_failure` for anything else, the output zeroed (<<hash-allocation>>).
