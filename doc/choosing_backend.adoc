[#hash-choosing-backend]
== Choosing a backend

A digest has one implementation, Boost.Hash2's or a C library's. A key
derivation has several, its backends: the same function, giving the same
bytes, in code of different size, speed and pedigree. A call that names no
backend takes the default, which is fixed: no measurement, link or define
changes it. This chapter says what the default is and why, how a program
names another backend, what each backend does with secrets and memory, and,
from the committed data, which backend has which function on which target,
and what each cost and allocated when it was measured.

[#hash-default-backend]
=== The default backend

[cols="2,1,3"]
|===
| Function | Default | Why

| `hkdf_extract`, `hkdf_expand`, `hkdf`, `pbkdf2`
| `hash2`
| the one backend that has every hmac, every operation and every target

| `argon2id`, `scrypt`
| `sodium`
| the one backend that has them; a program links `/third_party//sodium`

| a tag of `digest_of`, `hasher`, `mac` and `argon2`
| the first of `hash2`, `xkcp`, `blake3`, `sodium` that has it
| one stated rule: the backend that has the whole of the tag, else in part;
none when none of the four has it, and the call names its backend
|===

The families' defaults follow one rule and never change: the first of
`backends::hash2`, `backends::xkcp`, `backends::blake3` and
`backends::sodium` whose capability table, once increments 2 to 7 have
landed, has the tag whole (every option and output size the family accepts),
else the first of them that has it in part; `backends::bearssl`,
`backends::openssl` and the later backends are never a default. SHA-2's
and SHAKE's default is `hash2`, Keccak-256's `xkcp`, BLAKE3's `blake3`,
BLAKE2b's `sodium`; a tag none of the four has (SM3, Whirlpool, Argon2d) has
none, and its call names its backend. A default whose backend comes in a later
increment is already written: until it lands, a call on it stops the build.
If the program does not link that backend's library, the first message says
to add the library; once it is added, the next build stops with a message
that the tag is in no backend yet, or names the backends that have it.

The default is the same on every target, whatever the program links: linking
libsodium, BearSSL or OpenSSL makes their backends available to a call that
names them, never the default. `backends::hash2` is the default because it is
the only backend that covers every hmac, operation and target; it is
header-only, so a program carries only the functions it calls and shares the
SHA code it already uses for its digests; and the differences the reference
measurement found for HKDF are nanoseconds natively and a few KB of an
isolated program on WebAssembly (<<hash-measurements>>). No define chooses a
default: a program that wants another backend names it in the call, as the
second template argument, `hkdf<hmac_sha2_256, backends::openssl>`;
<<hash-kdfs-backends>> shows a program that does. A backend named in a call
that it lacks, or that the program does not link, stops the build with a
message that says what to do (<<hash-jamfile-messages>>), and so does OpenSSL
on Emscripten. `default_backend<Algorithm>` names the default at compile time.

[#hash-backend-conditions]
=== What each backend does with secrets and memory

webcpp's own code allocates nothing and wipes every secret intermediate it
holds (HKDF's blocks, PBKDF2's accumulators, each keyed copy of an hmac,
BearSSL's context) with stores the compiler cannot remove, on success and on
failure. What a C library or Boost.Hash2 does inside its own functions is
beyond its reach, and this table says what it is:

[cols="1,4"]
|===
| Backend | Its conditions

| `hash2`
| Boost.Hash2's own temporaries are not wiped: the padded key inside the
constructor of `hmac` and the inner digest of its `result()`. The digest types, and
`blake3` and `keccak_256`, do not wipe themselves on destruction.

| `sodium`
| Argon2id and scrypt allocate
the memory their costs name, with `mmap` where the system has it, else from
the C heap, outside any allocator of the program; libsodium's `sodium_init`
keeps its process-wide choice of implementations.

| `bearssl`
| hash wipes BearSSL's HKDF context before each call returns. BearSSL's own
temporaries on its stack, the pseudorandom key of `br_hkdf_flip` and the
padded keys of its HMAC, are not wiped: they stay in the stack memory of the
call until it is reused. BearSSL allocates nothing.

| `openssl`
| OpenSSL allocates a KDF and a context in every call, through its own
allocator, and frees both before the call returns. It clears the key (HKDF's
IKM or PRK, PBKDF2's password) and the info when it frees the context; it
frees the salt without clearing it. Its first call reads OpenSSL's
configuration file. It holds some lengths in an `int`, so hash refuses, before
OpenSSL is called, a PBKDF2 output (`invalid_output_size`), a PBKDF2 password
or salt, or an HKDF salt (`input_too_long`) of more than `INT_MAX` bytes. It
is not built for Emscripten.

| `xkcp`
| Hashes without a secret of their own; it allocates nothing.

| `blake3`
| Allocates nothing. Its keyed and `derive_key` modes hold the key in the
object's state until it is destroyed, without wiping it (<<hash-blake3>>).
|===

No backend states that its key derivations run in constant time; the
capability table records each upstream's statement, or the absence of one,
with its source, and the matrices below show it.

[#hash-measured]
=== The measured data

The chapters that follow are generated from data that tests and measurements
produce, never typed: the capability table, `doc/capabilities.json`, renders
which backend has each function on which target, over which hmacs, and its
constant time and the default of each function; the measured table,
`doc/measurements.json`, the size of a program per backend and target and the
throughput of each, a reference measured once, on 2026-11-16, that decides
nothing; the benchmark the owner named, PBKDF2-HMAC-SHA-512 at 1,000,000
iterations, its times; and the counting test, the allocations of each C
library.
